Graphile Worker, from job insertion to production operation

A practical explanation of how Graphile Worker works, what guarantees it gives, where it excels, where it becomes the wrong tool, and how it maps onto the TT Players scraping and ETL pipeline.

TT Players verdict: keep Graphile Worker. It matches the PostgreSQL-first, asynchronous ETL workload well. The important discipline is to design every task for at-least-once delivery, keep business workflow state in application-owned tables, and avoid depending on Graphile Worker’s private schema.
DurableJobs live in PostgreSQL and can be inserted transactionally.
Low infrastructureNo Redis, RabbitMQ, or separate cron service required.
At least onceTasks must be idempotent because retries can repeat effects.

1. What Graphile Worker is

Graphile Worker is a background job queue for Node.js applications that stores queue state in PostgreSQL. Application code or SQL inserts jobs; one or more worker processes claim runnable jobs and execute matching task functions.

Task

A named type of work, such as scrapeUrlTask, implemented by a JavaScript or TypeScript function.

Job

A durable invocation record containing a task identifier, JSON payload, schedule, attempts, priority, queue and optional job key.

Runner

The long-running process that maintains workers, claims jobs, invokes task executors and handles success or failure.

Useful mental model: a task is code; a job is data asking Graphile Worker to execute that code.

2. Architecture

The queue is not a separate server. It is a PostgreSQL schema plus Node.js worker processes. PostgreSQL provides durable storage, locking and transactions; the Node runner provides task execution and orchestration.

Key mechanisms

LISTEN/NOTIFY

When a producer inserts a job, PostgreSQL can notify listening workers so they wake quickly rather than waiting for the next poll.

Polling fallback

Workers still poll periodically. This protects against missed notifications and discovers delayed jobs when their run_at time arrives.

FOR UPDATE SKIP LOCKED

Concurrent workers can safely claim different rows without waiting behind one another. A locked job is skipped by other claimers.

PostgreSQL transactions

A business write and its follow-up job can be committed atomically, avoiding the classic “data committed but message publication failed” gap.

3. The lifecycle of a job

EnqueueA producer calls addJob, addJobs, or the PostgreSQL graphile_worker.add_job function. The job is persisted with its payload and execution options.
Become runnableThe job is eligible when its scheduled time has arrived, attempts remain, dependencies encoded by the application are satisfied, and its named queue is available.
ClaimA worker claims the row under PostgreSQL locking. Other workers skip the locked row and look for other work.
ExecuteThe registered task function receives the JSON payload and helpers such as logging, SQL access and job insertion.
Succeed or failReturning or resolving means success. Throwing or rejecting means failure.
Complete or retrySuccessful jobs are normally removed. Failed jobs record the error and are rescheduled with backoff until maxAttempts is exhausted.
await addJob('refreshPlayerStats', {
  playerId
}, {
  jobKey: `refresh-player:${playerId}`,
  maxAttempts: 5,
  priority: 50
});

4. Delivery guarantees and idempotency

Graphile Worker guarantees at-least-once execution, not exactly-once business effects. Most jobs run once, but a retry can occur after a task error, process crash, connection loss or uncertainty around completion.

Critical rule: assume any job may run more than once, even when duplicates are rare.

Why duplicates can happen

A task may complete an external side effect and then crash before the queue records success. From the queue’s perspective, retrying is the safe choice; from the external system’s perspective, the action may already have happened.

Good idempotency patterns

Database upsert

Use stable unique keys and INSERT ... ON CONFLICT DO UPDATE so repeating the same write converges on the same state.

Processing ledger

Record a domain event or source payload ID as processed under a unique constraint before applying dependent state changes.

External idempotency key

When an API supports it, send a stable request key so retries do not create duplicate payments, messages or resources.

Transactional state transition

Lock the domain row, verify its expected current state, perform the transition and record completion in one database transaction.

What job keys do—and do not—solve

A jobKey can replace, update or deduplicate queued work. It reduces redundant jobs, but it does not make the task body exactly once. A worker can still retry the same keyed job after partial execution.

6. How TT Players uses it

TT Players uses Graphile Worker in library mode as the scheduler and dispatcher for a PostgreSQL-centred ETL system.

Producers

Cron entries and task functions enqueue scraping, parsing, reconciliation, rating, cache and read-model work.

Runner

apps/worker/src/worker.ts creates a dedicated PostgreSQL pool, runs Graphile migrations, performs startup recovery and starts the worker.

Task registry

apps/worker/src/task-list.ts maps stable task identifiers to executor functions and schedules follow-up jobs.

Domain durability

Raw scrape data and application processing state live in TT Players tables, allowing parser fixes and reprocessing without relying only on queue history.

Representative pipeline

Scheduled discoveryFind active league or tournament targets
→
Scrape & preserveFetch source data, hash it and store recoverable raw input
→
Parse & publishUpsert domain tables, reconcile players, refresh ratings and read models

What the repository is doing well

  • Stable job keys reduce duplicate scrape and refresh work.
  • Retry policies are centralised rather than invented independently by each task.
  • Cron backfill is enabled for daily jobs.
  • Worker concurrency and PostgreSQL pool size are explicitly bounded.
  • Raw source payloads and domain state provide recoverability beyond the queue itself.
  • Graceful signal handling closes the runner and database pools.

Specific risks to address

Private schema dependency

startup-recovery.ts reads or updates graphile_worker._private_jobs and _private_tasks. These are implementation details and may change across releases. Prefer stable views/functions or application-owned recovery records.

Runtime upgrade gate

The repository currently allows Node 18 and declares Graphile Worker ^0.16.6. Current Graphile Worker documentation requires Node 22.18+ and PostgreSQL 12+, so runtime alignment and upgrade testing should happen together.

Manual retry policy

Resetting exhausted jobs based on parsed error text can accidentally re-run a permanently failing task. Recovery rules should be explicit, bounded and observable.

Single workload pool

Long scrapes, lightweight cleanup and rating calculations compete for the same concurrency. Named queues or separate worker processes may become useful as load grows.

7. Advantages and disadvantages

Advantages

  • One fewer infrastructure system to deploy, secure, back up and monitor.
  • Transactional enqueue with application database writes.
  • Strong durability from PostgreSQL.
  • Simple Node.js task model and TypeScript-friendly library API.
  • Retries, delayed work, cron, priorities and serial queues are built in.
  • Multiple worker processes can scale horizontally.
  • Operational inspection is possible with familiar SQL tooling.

Disadvantages

  • Queue writes, vacuum work and contention share resources with the main database.
  • At-least-once execution pushes idempotency responsibility into application design.
  • Not a full workflow engine with durable multi-step histories and signals.
  • PostgreSQL connection limits constrain worker and application pool sizing.
  • Large payloads bloat tables and WAL; jobs should carry references, not documents.
  • Cross-region active-active queueing is not its natural deployment model.
  • Private schema access is tempting but creates upgrade fragility.

8. Best applications

Graphile Worker is strongest when PostgreSQL is already central, the team wants low operational overhead, and work can be represented as bounded asynchronous tasks.

ETL and ingestion

Scraping, importing files, normalising records, deduplicating entities and refreshing read models.

Application background work

Email delivery, notifications, webhooks, document generation, image processing and cache refreshes.

Scheduled maintenance

Cleanup, snapshots, reports, data expiry, reconciliation and periodic health checks.

Transactional follow-ups

Commit domain changes and enqueue subsequent work in the same PostgreSQL transaction.

Moderate fan-out

Split a parent operation into many bounded child jobs while retaining retry and visibility.

Small-to-medium teams

Gain a reliable queue without dedicating engineering effort to another distributed system.

9. When to avoid it

Extreme sustained throughput

If queue traffic itself is massive and would dominate the primary database, a specialised broker or managed queue may isolate load better.

CPU-heavy workloads

Video encoding, large ML inference or heavy simulations need dedicated compute scheduling. Graphile Worker can dispatch them, but should not make the Node process do the work.

Complex long-running workflows

Human approvals, durable timers over months, external signals, workflow versioning and compensation logic fit systems such as Temporal more naturally.

Event streaming and replay

If the primary requirement is ordered streams, consumer groups, long retention and broad replay, Kafka-compatible systems are a better abstraction.

No PostgreSQL dependency

Introducing PostgreSQL only for the queue usually removes the simplicity advantage.

Independent failure domain required

If the queue must remain fully available while the application database is unhealthy or under maintenance, separating them may be worth the extra operations.

11. Production checklist

Task design

  • Make every task idempotent.
  • Keep payloads small and reference application rows.
  • Validate payloads at the executor boundary.
  • Use explicit timeouts for external calls.
  • Separate retryable and permanent failures where possible.

Capacity

  • Budget all PostgreSQL pools together.
  • Measure queue depth and oldest runnable-job age.
  • Control concurrency per external dependency.
  • Watch WAL, vacuum, table growth and database I/O.
  • Scale workers only after measuring the downstream bottleneck.

Observability

  • Use structured logs with task, job and domain identifiers.
  • Alert on exhausted jobs and increasing queue age.
  • Track execution duration, retry count and success rate per task.
  • Expose a safe operational view rather than querying private tables.
  • Document replay and manual recovery procedures.

Deployment

  • Run migrations before workers accept jobs.
  • Use graceful shutdown with adequate termination time.
  • Test rolling deployments with old and new task code overlapping.
  • Preserve backwards-compatible payload handling during rollout.
  • Pin and test upgrades that alter the queue schema.

1. What is the most accurate description of a Graphile Worker job?

Answer: B. The task is code; the job is persisted data describing one invocation.

2. Why does Graphile Worker combine notifications with polling?

Answer: C. LISTEN/NOTIFY wakes workers quickly, while polling is the reliability fallback.

3. What delivery model must task code assume?

Answer: A. Retries are necessary for durability, so task effects must be idempotent.

4. A job sends an email and the process crashes before recording success. What can happen?

Answer: B. This is the classic uncertain-completion case behind at-least-once delivery.

5. What is a named queue mainly used for?

Answer: C. Named queues are useful for per-resource exclusion and controlled access to a dependency.

6. Does a jobKey make the task body exactly once?

Answer: B. Job keys reduce redundant queued work; they do not remove the need for idempotency.

7. Why is Graphile Worker especially suitable for TT Players?

Answer: A. The existing database and workload make PostgreSQL-native queueing a natural fit.

8. Which TT Players behaviour most strongly supports safe retries?

Answer: C. These make repeated processing converge and allow recovery after parser failures.

9. What is the main upgrade risk currently called out for TT Players?

Answer: B. Private tables are not a stable public contract and can change between releases.

10. Which requirement points away from Graphile Worker?

Answer: C. A durable workflow engine is a more natural abstraction for long-lived stateful workflows.
